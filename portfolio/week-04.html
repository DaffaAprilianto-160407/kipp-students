Five-Language Translation Portfolio

Fondasi
Language
Satu meaning untuk lima person atau character.

Kompetensi target

Mengadaptasi repertoire dan language tanpa mengubah core meaning.

Evidence wajib

  • Lima versi untuk friend, technical peer, manager, customer, dan public.
  • Alasan perubahan language dan repertoire.
  • Feedback understanding dari sedikitnya satu target.
TipLihat contoh pengisian

Buka contoh fiktif Minggu 4 untuk melihat tingkat kekonkretan evidence dan analisis. Jangan menyalin contoh sebagai evidence pribadi.

Konteks performance

Tanggal dan setting: Tahap awal: 27 September 2026, tiga percakapan terpisah lewat chat WhatsApp (T, D, H). Tahap revisi setelah asesmen: 5 Oktober 2026, dua percakapan WhatsApp tambahan (J dan A).

Persons dan relationship:

  • T — teman satu kuliah, mahasiswa Fakultas Kedokteran Gigi (FKG). Dipilih untuk versi Friend karena bidangnya jauh dari IT.
  • D — teman sejurusan Sistem dan Teknologi Informasi. Dipilih untuk versi Technical peer karena punya latar belakang teknis yang setara untuk menilai presisi istilah.
  • H — teman SMA, sekarang kuliah Manajemen di universitas berbeda. Diminta roleplay sebagai manajer untuk versi Manager. Karena H memang berlatar belakang manajemen, responsnya dinilai sebagai kecocokan register dengan cara berpikir bisnis, bukan bukti bahwa versi ini bisa mengubah pola pikir orang yang benar-benar awam bisnis.
  • J — teman, mahasiswa non-IT. Dipilih untuk versi Customer karena memakai aplikasi sehari-hari sebagai pengguna, bukan dari bidang IT. J menjawab sebagai dirinya sendiri, bukan roleplay.
  • A — orang tua, non-IT. Dipilih untuk versi Public karena diperkirakan benar-benar awam teknologi. Semua balasan A di tahap revisi berstatus teks berlabel AI (lihat Evidence 5 dan Batas evidence), sehingga profil A di bawah belum terverifikasi.

Objective dan initial state:

Objective: menyampaikan makna inti API dalam lima ragam bahasa tanpa mengubah core meaning, lalu memverifikasi pemahaman lewat target nyata untuk sebanyak mungkin ragam.

Initial state per target:

D Sejurusan STI, dipakai untuk uji presisi istilah, bukan uji pemahaman awam Tidak diukur

Karena J sudah paham API sejak awal, hasil tes J menguji kejelasan saran dan reaksi terhadap kata “jembatan (API)”, bukan pembelajaran konsep.

Core meaning yang tidak boleh berubah, dipecah menjadi tiga klaim:

  • K1: API menghubungkan dua sistem atau aplikasi yang berbeda.
  • K2: Penghubungan itu memungkinkan keduanya bertukar data dan bekerja sama.
  • K3: Salah satu pihak tidak perlu mengetahui cara kerja internal pihak lainnya.

Pengecekan tiap versi terhadap tiga klaim ini ada di bagian Analisis komunikasi.

T, D, dan J adalah orang sungguhan; H roleplay.

Kondisi awal J nyata dan menunjukkan ia sudah paham API; kondisi awal A tidak bisa diandalkan karena berlabel AI. Kondisi awal T, D, dan H pada tahap awal tidak diukur.
Repertoire & language Register berbeda kontras: analogi sehari-hari (Friend), istilah presisi industri (Technical peer), kerangka biaya-risiko-revenue (Manager), langkah tindakan konkret (Customer), dan keamanan serta kemudahan sehari-hari (Public). Relationship outcome Percakapan dengan T, D, H, dan J berlangsung santai dan kooperatif. Setelah balasan A terdeteksi bercirikan AI, saya memutuskan tidak meminta A mengulang lewat voice note demi menjaga kenyamanan beliau, dan menandai bagian itu sebagai belum teruji.

Batas evidence:

  • Public: satu-satunya respons untuk versi Public (A) berlabel AI. Ia hanya menunjukkan bahwa versi Public terbaca jelas oleh model bahasa dengan persona “orang tua awam”, bukan bukti bahwa orang awam sungguhan memahaminya. Versi Public berstatus belum teruji ke orang awam sungguhan.
  • Customer: J sudah mengenal API sejak awal, jadi tes J menguji kejelasan saran dan reaksi terhadap kata “jembatan (API)”, bukan apakah konsep dapat dipahami orang yang belum mengenalnya. Hanya satu orang untuk audiens ini.
  • Manager: H memiliki latar belakang manajemen dan hanya roleplay, sehingga responsnya sebagian dipengaruhi latar pendidikan dan bukan keputusan bisnis nyata.
  • Technical peer: D sesama mahasiswa STI, sehingga validasinya soal presisi istilah, bukan keterpahaman orang awam. D tidak menjawab secara eksplisit pertanyaan tentang istilah yang kurang presisi.
  • Percobaan A: percobaan lewat WhatsApp menghasilkan balasan yang memuat kalimat pembuka khas asisten AI, sehingga tidak dihitung sebagai respons A sendiri. Pelajaran: evidence lewat chat perlu diverifikasi keasliannya, terutama bila penerima bisa dibantu aplikasi atau orang lain.
  • Catatan dosen: menurut penyampaian dosen kepada saya, percakapan dengan AI diperbolehkan dalam latihan ini, sehingga respons A tetap dicantumkan dengan label yang jelas.

Penggunaan AI

  • Alat dan peran AI: Claude (Anthropic). Tahap awal: menjelaskan tugas
  • Prompt atau instruksi penting: jelaskan ke pada ku tugas ini.
  • Bagian output yang digunakan, diubah, atau ditolak: Digunakan: draf lima versi, pesan uji, skrip pesan kondisi awal untuk J dan A, dan usulan revisi versi Customer (menambah langkah cek saldo dan melunakkan klaim penyebab). Diubah: skor Person & Character dan Response & Adaptation diperbarui mengikuti evidence terbaru; pecahan core meaning menjadi tiga klaim; catatan analisis membedakan evidence “adaptasi” (T) dari evidence “validasi” (D, H). Dikeluarkan dari status evidence langsung: balasan A. Awalnya saya menganggap balasan A sebagai respons A sendiri; setelah pemeriksaan, kalimat pembuka khas AI membuat saya mencatatnya sebagai teks berlabel AI, tanpa mengubah satu kata pun dari isinya.
  • Pemeriksaan accuracy, privacy, dan authority: Accuracy: pesan dan respons T, D, H, J, dan A ditranskrip apa adanya dari screenshot, tidak dihaluskan, termasuk kalimat pembuka AI pada balasan A. Privacy: semua target hanya disebut dengan inisial dan relasi/profil umum. Authority: keputusan skor akhir dan interpretasi evidence tetap ada pada saya, bukan pada AI.
  • Apa yang tetap dipelajari sebagai manusia: Latar belakang penerima memengaruhi seberapa “berhasil” sebuah versi bahasa terlihat (jurusan H, pengetahuan awal J), sehingga evidence yang baik perlu menyebutkan konteks penerima. Saya juga belajar bahwa evidence lewat chat perlu dicek keasliannya, dan bahwa kondisi awal target harus ditanyakan sebelum versi dikirim, bukan sesudahnya.

Feedback dan tindak lanjut

Feedback yang diterima:

  • T: awalnya “iya paham”, lalu lewat teach-back menjelaskan API sebagai penghubung dua sistem independen.
  • D: menjelaskan ulang mekanisme API (client-server, HTTP, method CRUD, format data, autentikasi, rate limiting) secara akurat tanpa koreksi.
  • H: mengevaluasi API sebagai peluang monetisasi dan mempertimbangkan risk mitigation cost serta langkah bisnis lanjutan.
  • J: jawaban atas pertanyaan kondisi awal dan atas versi Customer revisi dicatat di Evidence 4.
  • A: tidak dihitung sebagai feedback langsung karena berlabel AI. Isinya hanya menunjukkan versi Public terbaca jelas oleh model bahasa.

Adaptation/replay:

  • T: saya menambah langkah teach-back karena jawaban awal terlalu singkat untuk dijadikan bukti.
  • Customer: versi direvisi sebelum diuji (versi awal → revisi, alasan, dan perubahan ada di bawah tabel Evidence). Hasil pengiriman versi revisi ke J dicatat di Evidence 4; belum ada putaran perbaikan setelahnya.
  • Public: tidak ada revisi. Satu-satunya respons berlabel AI dan tidak menunjukkan kebingungan nyata, jadi saya tidak mengubah versi tanpa bukti. J dan A sama-sama awalnya mengira “API” sebagai api sungguhan; versi Public menempatkan istilah “API” dalam kurung setelah konsepnya dijelaskan, dan akan dievaluasi ulang bila penguji lisan juga tersandung di kata itu.
  • D dan H: tidak ada revisi karena respons keduanya sudah menunjukkan pemahaman akurat sesuai register masing-masing.

Next practice:

  1. Menguji versi Public secara lisan ke orang awam teknologi yang bisa ditemui langsung, dengan kondisi awal ditanyakan lebih dulu dan jawaban dicatat sendiri.
  2. Menguji versi Manager ke satu pengambil keputusan nyata (ketua organisasi, kakak tingkat, atau dosen), bukan roleplay.
  3. Menanyakan lagi ke D dengan pertanyaan lebih sempit, misalnya apakah versi teknis hanya cocok untuk web/REST API atau API secara umum.
  4. Menetapkan core meaning dan menanyakan kondisi awal target sebelum mengirim versi apa pun.
